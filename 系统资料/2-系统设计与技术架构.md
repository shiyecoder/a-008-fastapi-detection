# 基于FastAPI+Vue的Webshell检测平台的设计与实现 - 系统设计与技术架构

## 一、系统总体架构

### 1.1 系统架构图

```
         ┌─────────────────────────────┐
         │Vue 3 + Element Plus 管理端  │
         │http://localhost:5170        │
         └──────────────┬──────────────┘
                        │  HTTP / JSON
                        ▼
┌───────────────────────────────────────────────┐
│FastAPI 应用服务（端口 8080）                  │
├───────────────────────────────────────────────┤
│  Blueprint / Router（72 条路由）              │
│  处理函数（参数校验 + 业务调用）              │
│  ORM 模型层（15 个模型）                      │
│  工具与鉴权装饰器                             │
└───────────────────────┬───────────────────────┘
                        │  JDBC / PDO / PyMySQL
                        ▼
┌───────────────────────────────────────────────┐
│MySQL 库：webshell_platform                    │
│15 张业务表                                    │
└───────────────────────────────────────────────┘
```

### 1.2 技术架构说明

| 层次 | 载体 | 职责 |
|------|------|------|
| 路由层 | Blueprint / APIRouter | 按模块拆分路由，统一前缀注册 |
| 视图层 | route 函数 | 参数解析、鉴权装饰器、业务调用 |
| 模型层 | ORM Model | SQLAlchemy 模型与表映射 |
| 工具层 | utils / deps | Token 解析、统一响应、异常处理 |

请求自上而下穿过各层，返回值再自下而上封装。登录态校验通过装饰器注入到每个接口函数上。

### 3.2 核心类与关键实现

#### 3.2.1 典型控制器方法 `router.list_alerts`

以 `/alert/page` 接口为例，方法体展示了参数绑定、Service 调用与统一返回的完整写法：

```php
public Object list_alerts() q = db.query(Alert)
if keyword:
    q = q.filter(Alert.title.like(f"%{keyword}%"))
if severity:
    q = q.filter(Alert.severity == severity)
if status:
    q = q.filter(Alert.status == status)
if alert_type:
    q = q.filter(Alert.alert_type == alert_type)
total = q.count()
rows = q.order_by(Alert.id.desc()).offset((page - 1) * pageSize).limit(pageSize).all()
return ok(page_data([{
    "id": a.id, "title": a.title, "alert_type": a.alert_type,
    "severity": a.severity, "source": a.source, "description": a.description,
    "status": a.status, "handler": a.handler, "handle_remark": a.handle_remark,
    "handle_time": a.handle_time, "create_time": a.create_time,
} for a in rows], total, page, pageSize))
```

### 3.4 接口响应规范

通用响应结构：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { }
}
```

约定 `code=200` 表示成功，非 200 时 `message` 携带可直接展示给用户的错误文案；分页数据统一放在 `data.records`（或 `data.list`）+ `data.total` 中，前端表格组件直接消费。

## 六、安全设计

| 安全项 | 措施 |
|------|------|
| 认证机制 | 登录成功后签发 Token，后续请求在请求头携带；服务端拦截器统一校验。 |
| 密码存储 | 密码不以明文形式返回给前端，登录校验在服务端完成。 |
| 接口权限 | 管理端接口与前台接口分开前缀（`/api/admin` 与业务接口），拦截器按角色判断是否放行。 |
| SQL 注入 | 使用 ORM 或 MyBatis `#{}` 占位符 / PDO 预处理，不拼接用户输入。 |
| 文件上传 | 限制扩展名与大小，保存到独立目录，文件名用时间戳重命名，避免覆盖与路径穿越。 |
| 越权防护 | 查询与修改操作均带当前登录用户 ID 作为条件，防止通过改 URL 参数访问他人数据。 |

## 七、性能优化

| 优化点 | 做法 |
|------|------|
| 索引 | 主键与常用查询字段（如 `sys_user`、`sys_role`、`sys_menu`）建立索引，15 张表带显式索引定义。 |
| 前端按需加载 | 路由使用懒加载 `() => import()`，首屏只加载当前页面组件。 |
| 静态资源 | 图片统一存放于 `uploads` / `static` 目录，由服务端直接返回，避免重复读写数据库。 |
| 连接池 | 数据库连接由框架连接池统一管理（SQLAlchemy Pool），避免每次请求新建连接。 |
