# 基于FastAPI+Vue的Webshell检测平台的设计与实现 - 总结与展望

## 一、工作总结

### 1.1 项目概述

本课题围绕信息服务场景，设计并实现了一套Webshell检测平台。系统以 **FastAPI + Vue 3.x + MySQL 8.0** 为技术栈，共设计 15 张数据表、72 个接口、2 个功能模块，覆盖线路、公共等业务流程。

Webshell 检测平台。面向 Web 安全运维，把可疑文件上传后并行执行哈希黑名单、静态签名、YARA 规则与动态行为四类检测，覆盖 PHP、JSP、ASP、Python 规则；命中即生成告警，可一键隔离并支持还原，处置过程留痕成报告。规则库在前端即可增删启停、无需重启。扫描记录按时间归档，支持按文件类型与命中规则回溯历史检测，便于复盘攻击链路。技术栈为 FastAPI + Vue 3 + SQLite。

### 1.2 完成的主要工作

### 1.3 技术创新点

#### 1.3.1 基于角色的权限模型

用户表与角色表分离，`sys_user` 记录账号与角色归属，登录后按角色加载菜单与接口权限，新增角色不需要改代码。

#### 1.3.2 数据统计与可视化

系统内置 10 个统计类接口（如 `/dashboard/overview`），按时间、分类、状态等维度聚合，前端用图表组件直接渲染，管理者不必手工导出 Excel 再制图。

#### 1.3.3 文件与图片管理

上传接口统一处理类型校验、大小限制与重命名，图片按业务分目录存放，数据库只存相对路径，迁移环境时不需要改数据。

#### 1.3.4 智能能力接入

系统通过 `/alert/handle/{aid}` 等接口接入模型能力，把非结构化的文本/图片转换为结构化结果，再落库供业务使用；模型调用与业务逻辑解耦，便于更换后端。

### 1.4 系统特色

- **开箱可运行**：导入 SQL、改一处数据库配置即可启动，不依赖第三方服务。
- **结构规范**：分层清晰，命名统一，新增业务按同一模式扩展。
- **数据留痕**：关键表带创建时间、更新时间与操作人，便于追溯。
- **界面统一**：沿用成熟组件库的交互规范，学习成本低。
- **覆盖完整**：15 张表覆盖了主数据、业务单据与统计维度，不是只有增删改查的演示。

## 二、遇到的问题与解决方案

### 2.1 技术问题

**多表写入的一致性**

问题：新增主表与明细时，若中途失败会留下“有主表无明细”的脏数据。

解决：把写操作放进同一事务，任一环节异常直接回滚；对必须唯一的业务编号加唯一索引，由数据库兜底。

**列表页重复代码**

问题：十几个列表页的搜索、分页、删除逻辑几乎一样，改动要改多处。

解决：抽出通用的表格页组件，页面只声明列定义与接口地址，公共逻辑收敛到组件内。

### 2.2 设计问题

问题：早期把业务判断写在了页面里，导致同一规则在小程序端与后台端各写一遍，改一处漏一处。

解决：把校验、状态流转、金额计算下沉到服务端，页面只负责收集参数与展示结果；两端调用同一接口，规则只有一份。

## 三、系统展望

### 3.1 短期改进

- 补充操作日志表，记录谁在什么时间改了什么，满足审计要求；
- 列表页增加导出 Excel 功能，方便线下汇总；
- 完善表单的行内校验提示，减少提交后才报错的情况。

### 3.2 中期改进

- 引入缓存（Redis）存放字典与热点数据，降低数据库压力；
- 把文件存储从本地磁盘迁移到对象存储，支持多实例部署；
- 增加消息通知（站内信 / 模板消息），让状态变更主动触达用户。

### 3.3 长期方向

- 按业务域拆分服务，接口层加网关统一鉴权与限流；
- 沉淀数据仓库，把业务数据按主题建模，支撑更复杂的分析；
- 在现有数据基础上引入推荐 / 预测模型，从“记录业务”走向“辅助决策”。

### 3.4 技术升级路线

| 阶段 | 目标 | 涉及技术 |
|------|------|------|
| 当前 | 单体应用，单机部署 | FastAPI + MySQL |
| 近期 | 读写分离、缓存加速 | Redis + 主从复制 |
| 中期 | 服务拆分、容器化 | Docker + 网关 |
| 远期 | 数据分析与智能决策 | 数据仓库 + 模型服务 |
